## Integration Points

### 1. DBService
HTTP wrapper around MS SQL DB, hosted in the same environment as ClientAPI.

- Config section: `DbService` → `DbServiceOptions`
- Interface + implementation: `IDbServiceClient` / `DbServiceClient` (in `Services/Integrations/`)
- Named `HttpClient`: `"DbService"`

### 2. Original Core Data Service
The legacy "Original" external Core data service.

- Interface + implementation: `IOriginalCoreDataServiceClient` / `OriginalCoreDataServiceClient` (in `Services/Integrations/`)
- Named `HttpClient`: `"OriginalCoreDataService"`
- Response model: `OriginalCoreDataResponse` — **do not merge with `NewCoreDataResponse`**

### 3. New Core Data Service
The newer "New" external Core data service.

- Interface + implementation: `INewCoreDataServiceClient` / `NewCoreDataServiceClient` (in `Services/Integrations/`)
- Named `HttpClient`: `"NewCoreDataService"`
- Response model: `NewCoreDataResponse` — **do not merge with `OriginalCoreDataResponse`**

> There is **no shared `ICoreDataServiceClient` abstraction** and **no centralized resolver**. The two clients have different I/O specs.

## OSR Routing Pattern

Most endpoints:
1. Accept a JSON body containing an `osr` field (type `Osr` enum).
2. **Inject both `IOriginalCoreDataServiceClient` and `INewCoreDataServiceClient` directly into the service** — there is no shared abstraction or centralized resolver.
3. Read `IOptionsMonitor<CoreDataServiceOptions>.CurrentValue.OsrMappings` to determine which client to use for the given `osr` value.
4. Branch inline on `CoreDataServiceType` to call the appropriate client and map its response to the use-case model.
5. Call `IDbServiceClient`.
6. Return a combined response.

> **Coupling is intentional.** The two Core data service clients have different I/O shapes (`OriginalCoreDataResponse` vs `NewCoreDataResponse`). Do **not** introduce a shared interface or resolver — that would diverge from the real codebase.
